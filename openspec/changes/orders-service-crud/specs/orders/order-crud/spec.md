# Spec Delta

## Purpose

Позволяет внутренним клиентам API создавать, читать, полностью заменять и удалять заказы через REST-интерфейс `/orders` с понятными ответами на невалидные данные и несуществующие заказы.

## ADDED Requirements

### Requirement: Создание заказа
Сервис MUST принимать `POST /orders` с телом заказа (`customerName`, `items`, необязательный `status`) и создавать заказ. Идентификатор заказа (`id`) и время создания (`createdAt`) MUST назначаться сервисом, значения из тела запроса для них игнорируются. Если `status` не передан, заказ MUST получить статус `NEW`.

#### Scenario: AC-1 Создание заказа с валидными данными
- **GIVEN** тело запроса с непустым `customerName` и непустым списком `items` с корректными позициями, без `status`
- **WHEN** клиент отправляет `POST /orders`
- **THEN** сервис отвечает 201, заголовок `Location` указывает на `/orders/{id}` созданного заказа
- **AND** тело ответа содержит заказ с `id`, `createdAt`, переданными `customerName` и `items` и статусом `NEW`

#### Scenario: AC-2 Создание заказа с пустым или невалидным по формату телом
- **WHEN** клиент отправляет `POST /orders` с пустым телом или с телом, не являющимся корректным JSON
- **THEN** сервис отвечает 400
- **AND** заказ не создаётся

#### Scenario: AC-3 Создание заказа без имени клиента
- **WHEN** клиент отправляет `POST /orders`, где `customerName` отсутствует, равен `null` или пуст
- **THEN** сервис отвечает 400
- **AND** заказ не создаётся

#### Scenario: AC-4 Создание заказа без позиций
- **WHEN** клиент отправляет `POST /orders`, где `items` отсутствует, равен `null` или пуст
- **THEN** сервис отвечает 400
- **AND** заказ не создаётся

#### Scenario: AC-5 Создание заказа с некорректной позицией
- **WHEN** клиент отправляет `POST /orders`, где у позиции `productName` пуст, или `quantity` не больше 0, или `price` отрицательна
- **THEN** сервис отвечает 400
- **AND** заказ не создаётся

#### Scenario: AC-6 Создание заказа с неизвестным статусом
- **WHEN** клиент отправляет `POST /orders` со `status`, не входящим в `NEW`, `CONFIRMED`, `CANCELLED`
- **THEN** сервис отвечает 400
- **AND** заказ не создаётся

### Requirement: Получение списка заказов
Сервис MUST возвращать по `GET /orders` все существующие заказы по возрастанию `createdAt`; при равенстве `createdAt` — в порядке создания.

#### Scenario: AC-7 Список заказов в порядке создания
- **GIVEN** в сервисе созданы несколько заказов
- **WHEN** клиент отправляет `GET /orders`
- **THEN** сервис отвечает 200 и возвращает все заказы по возрастанию `createdAt`

#### Scenario: AC-8 Пустой список заказов
- **GIVEN** в сервисе нет заказов
- **WHEN** клиент отправляет `GET /orders`
- **THEN** сервис отвечает 200 и возвращает пустой список

### Requirement: Получение заказа по идентификатору
Сервис MUST возвращать по `GET /orders/{id}` заказ с указанным `id`. Значение `id` в пути, не являющееся UUID, MUST приводить к ответу 400 раньше, чем проверяется существование заказа.

#### Scenario: AC-9 Получение существующего заказа
- **GIVEN** существует заказ с некоторым `id`
- **WHEN** клиент отправляет `GET /orders/{id}`
- **THEN** сервис отвечает 200 и возвращает этот заказ

#### Scenario: AC-10 Получение несуществующего заказа
- **GIVEN** заказа с указанным корректным UUID не существует
- **WHEN** клиент отправляет `GET /orders/{id}`
- **THEN** сервис отвечает 404

#### Scenario: AC-11 Получение заказа по не-UUID идентификатору
- **WHEN** клиент отправляет `GET /orders/{id}`, где `id` не является UUID
- **THEN** сервис отвечает 400, а не 404

### Requirement: Полная замена заказа
Сервис MUST заменять по `PUT /orders/{id}` изменяемые поля существующего заказа (`customerName`, `items`, `status`) значениями из тела запроса; тело MUST быть полным и проходить те же проверки, что и при создании. `id` и `createdAt` MUST оставаться неизменными, значение `id` из тела MUST игнорироваться. `PUT` MUST NOT создавать заказ. Значение `id` в пути, не являющееся UUID, MUST приводить к ответу 400 раньше, чем проверяется существование заказа.

#### Scenario: AC-12 Замена существующего заказа
- **GIVEN** существует заказ с некоторым `id`
- **WHEN** клиент отправляет `PUT /orders/{id}` с валидным телом, где изменены `customerName`, `items` и `status`
- **THEN** сервис отвечает 200 и возвращает обновлённый заказ
- **AND** `id` и `createdAt` заказа остаются прежними

#### Scenario: AC-13 Игнорирование идентификатора из тела при замене
- **GIVEN** существует заказ с некоторым `id`
- **WHEN** клиент отправляет `PUT /orders/{id}` с валидным телом, содержащим другой `id`
- **THEN** сервис отвечает 200, и изменяется заказ с `id` из пути, а `id` из тела не используется

#### Scenario: AC-14 Замена несуществующего заказа
- **GIVEN** заказа с указанным корректным UUID не существует
- **WHEN** клиент отправляет `PUT /orders/{id}` с валидным телом
- **THEN** сервис отвечает 404
- **AND** заказ не создаётся

#### Scenario: AC-15 Замена заказа невалидными данными
- **GIVEN** существует заказ с некоторым `id`
- **WHEN** клиент отправляет `PUT /orders/{id}` с пустым или битым телом, либо с неполным телом, либо с данными, нарушающими правила `POST` (пустой `customerName`, пустой `items`, `quantity` не больше 0, отрицательная `price`, неизвестный `status`)
- **THEN** сервис отвечает 400
- **AND** заказ остаётся без изменений

#### Scenario: AC-16 Замена заказа по не-UUID идентификатору
- **WHEN** клиент отправляет `PUT /orders/{id}`, где `id` не является UUID
- **THEN** сервис отвечает 400, а не 404

### Requirement: Удаление заказа
Сервис MUST удалять по `DELETE /orders/{id}` заказ с указанным `id`. Значение `id` в пути, не являющееся UUID, MUST приводить к ответу 400 раньше, чем проверяется существование заказа.

#### Scenario: AC-17 Удаление существующего заказа
- **GIVEN** существует заказ с некоторым `id`
- **WHEN** клиент отправляет `DELETE /orders/{id}`
- **THEN** сервис отвечает 204 без тела
- **AND** последующий `GET /orders/{id}` отвечает 404

#### Scenario: AC-18 Удаление несуществующего или уже удалённого заказа
- **GIVEN** заказа с указанным корректным UUID не существует, либо он уже был удалён
- **WHEN** клиент отправляет `DELETE /orders/{id}`
- **THEN** сервис отвечает 404

#### Scenario: AC-19 Удаление заказа по не-UUID идентификатору
- **WHEN** клиент отправляет `DELETE /orders/{id}`, где `id` не является UUID
- **THEN** сервис отвечает 400, а не 404

### Requirement: Формат ответа об ошибке
Сервис MUST возвращать на ответы 400 и 404 тело с полями `status` (равно HTTP-коду ответа), `error` и `message`. Тело ошибки MUST NOT содержать стек-трейс.

#### Scenario: AC-20 Единый формат тела ошибки
- **WHEN** сервис отвечает 400 или 404 на любую операцию `/orders`
- **THEN** тело ответа содержит поля `status`, `error` и `message`, где `status` равен HTTP-коду ответа
- **AND** тело ответа не содержит стек-трейс

### Requirement: Точность цены позиции
Сервис MUST принимать и возвращать `price` позиции заказа как JSON-число без потери точности.

#### Scenario: AC-21 Цена с дробной частью сохраняется точно
- **WHEN** клиент создаёт заказ с позицией, где `price` равна 10.50, а затем читает этот заказ
- **THEN** возвращённая `price` равна 10.50 без искажения

### Requirement: Корректность при одновременных запросах
Сервис MUST сохранять целостность заказов при одновременных запросах: не терять и не портить заказы и не отвечать 500 на параллельные операции.

#### Scenario: AC-22 Параллельное создание заказов
- **WHEN** клиенты одновременно отправляют 100 валидных `POST /orders`
- **THEN** `GET /orders` возвращает ровно 100 заказов с уникальными `id`

#### Scenario: AC-23 Параллельное изменение и удаление одного заказа
- **GIVEN** существует заказ с некоторым `id`
- **WHEN** клиенты одновременно отправляют `PUT /orders/{id}` и `DELETE /orders/{id}` для этого заказа
- **THEN** каждый ответ — 200, 204 или 404, ни один не равен 500
- **AND** итоговое состояние согласовано: заказ либо удалён, либо содержит данные одного из успешных `PUT`
